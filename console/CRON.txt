================================================================================
 GAMENTATOR — CRON / CONSOLE COMMANDS
================================================================================

Each command below is a Yii console action in console/controllers/.
Run inside the container, e.g.:

    docker compose exec php php yii steam/sync

Actual start/finish times of every run are recorded automatically in:

    console/runtime/logs/cron.log

(one "START <cmd>" line when it begins, one "END <cmd> (<seconds>s)" line when
it finishes — see CronLogger). That file is where you check "when did it run
and how long did it take".

--------------------------------------------------------------------------------
 COMMANDS  (suggested cadence — the real schedule lives in the server crontab)
--------------------------------------------------------------------------------

  steam/discover [--limit=500] [--verbose=1] [--shards=1] [--shard=0]
      Lightweight triage of the raw queue: one cheap appdetails call per new stub
      to classify it. Dead/region-locked appids -> success_false; types we don't
      enrich (music, video, demo, hardware…) -> inactive; real games/DLC get their
      cheap scalar fields stored and a type tag, which graduates them into the
      full-sync queue. This is what stops steam/sync wasting its ~9-request budget
      on junk. Runs on the type-null rows, sync on the type-tagged rows, so the two
      never collide and can run in parallel (and sharded — same --shards/--shard
      as steam/sync). Run this before/alongside steam/sync.
      Cadence: new appids arrive rarely (coming-soon + DLC stubs), so once the
      initial backlog is drained this only needs to run every few hours. Run it
      often only while first draining a large WAIT_TO_SYNC / type-null backlog.
      Drain progress: SELECT COUNT(*) FROM game WHERE status=0 AND type IS NULL;

  steam/sync [--limit=100] [--verbose=1] [--shards=1] [--shard=0]
      Pulls fresh Steam data for games waiting to sync / flagged force_sync.
      Only enriches games steam/discover has already triaged (keep-type stubs),
      plus force_sync re-syncs and long-stale refreshes.
      In practice the dominant load is force_sync: Game::checkSyncDate() flags
      every viewed game whose data is older than a day, and each flag triggers a
      full ~9-request re-sync — so the bottleneck is throughput, not new games.
      Cadence: often, small batches — e.g. every 5 min.
      Sharding (the lever for the force_sync backlog): run the same command on
      both boxes (each on its own IP, to stay under Steam's per-IP rate limit)
      with --shards=2 and a distinct --shard (0 on one, 1 on the other). Each
      worker takes a disjoint id-class (id % shards = shard) of the force_sync /
      new / stale queues, so they never sync the same game and need no
      coordination — roughly doubling drain rate.
        box A:  steam/sync 80 --shards=2 --shard=0
        box B:  steam/sync 80 --shards=2 --shard=1

  steam/get-coming-soon
      Discovers upcoming Steam titles, then recounts genres/tags/features.
      Cadence: daily.

  steam/create-app-list   [DEPRECATED — do not schedule]
      Abandoned: the ISteamApps/GetAppList endpoint it used is dead, and the
      full-catalogue seed flooded the sync queue with junk faster than it drained.
      The action is now a no-op that exits non-zero. New appids come from
      steam/get-coming-soon and the keyshop crawlers.

  steam-spy/create-app-list
      Seeds appids from SteamSpy.
      Cadence: weekly / occasional.

  sale/synchronize
      Refreshes Bestsellers / New & Noteworthy / Upcoming lists.
      Cadence: every 6 hours.

  instant-gaming/list-all   (cron entrypoint)
  instant-gaming/list <trending|pre-orders|bestsellers> [--verbose=1]
      Mirrors the Instant Gaming listing pages into homepage rails (each list its
      own game_sale type). Scrapes the ranked games off the page (inlined Algolia
      state for trending/pre-orders, the HTML card grid for bestsellers) and
      matches each to our catalogue:
        - a confident IG product-id match gets a live offer straight away;
        - an uncertain title match is parked in the Offers review queue and only
          surfaces once an admin accepts it.
      A game appears in the rail ONLY while it has an active IG offer — the
      game_sale row is just the ranking. An empty/failed fetch leaves the existing
      rail untouched (no wipe on a network blip). Per-list file lock, so a list
      can't overlap itself.
      list-all runs all three in one pass with a short sleep between them (one
      failing doesn't stop the rest) — this is what cron calls. The list <name>
      form is for a manual/targeted single run.
      Cadence: every few hours — the lists drift slowly.

  kinguin/match [<limit=100>] [--verbose=1] [--recheck=1]
  kinguin/refresh-prices [<limit=150>] [--verbose=1]
  kinguin/enrich-media [<limit=0>] [--verbose=1]
  kinguin/diagnose ["<title>"]
      Builds and refreshes Kinguin offers for our games (fourth store, alongside
      Instant Gaming / Gamivo / GameSeal). Kinguin has a first-party REST API
      (key in params-local.php's `kinguin_api_key`), and its products carry a
      Steam appid, so `match` keys off the appid (with a title/edition guard) —
      more precise than the title-only matching the other stores must use.
        - match (heavy, rare): search by title, match, create offers. Region-free
          matches publish straight away; region-locked ones go to the Offers
          review queue (STATUS_REVIEW) hidden until an admin accepts them.
        - refresh-prices (light, frequent): re-read price/stock for matched offers
          by their stored kinguinId — one precise API call each, no re-search.
          ALSO captures each product's trailer(s) + pre-order flag for free (the
          product is already fetched here), so the homepage "In motion" strip and
          the "Pre-order" badge stay fresh with no extra scheduling.
        - enrich-media: OPTIONAL one-shot backfill of the same trailers + pre-order
          flag for ALL already-matched offers, so the strip fills immediately
          instead of waiting for refresh-prices to cycle through every offer.
          Not for cron — run it once after deploy (or after a big match run).
        - diagnose: prints API/rates connectivity from this server; run it when
          everything comes back "no match" to rule out a bad key / rate limit.
      Prices are EUR, converted to the other currencies with ECB rates; Kinguin
      exposes no RRP, so offers have a final price but no struck-through original.
      Per-phase file lock, so a phase can't overlap itself.
      Cadence: match every ~15 min, refresh-prices a few minutes offset.

  genre/recount
  tag/recount
  category/recount
  developer/recount
  publisher/recount
      Refresh the precomputed games_count columns (drive the directories and
      landing pages). Genre/tag/category also run automatically after
      steam/get-coming-soon.
      Cadence: daily, after steam/sync.

  import/all   (or individually: import/developers, import/publishers)
      Runs every profile importer. Each scans its console/data/import/<kind>/
      drop folder for *.json files, upserts them by id, then deletes the file on
      success (or moves it to failed/ if unparseable).
      Safe to run often — only newly dropped files are read.
      Cadence: every 5 min.

  sitemap/generate [--baseUrl=https://gamentator.com]
      Regenerates the gzipped XML sitemap set + index.
      Cadence: daily, after the catalog sync.

--------------------------------------------------------------------------------
 EXAMPLE CRONTAB — TWO BOXES (different IPs, shared DB)
--------------------------------------------------------------------------------

 The dominant Steam load is the force_sync re-sync backlog, so steam/sync is
 sharded across both boxes (--shards=2, distinct --shard) to roughly double the
 drain rate. Everything else stays on box A only — one-shot jobs (get-coming-soon,
 sale, sitemap, recounts, geo-ip, cache flush) must NOT run on both or they
 duplicate work / double the API hits. New games are rare, so steam/discover runs
 infrequently (box A). steam-user/* hit a different Steam endpoint, so they don't
 compete with sync for the appdetails budget.

 --- BOX A (IP #1) -------------------------------------------------------------

  # m          h   command
  */5          *   * * *   php yii steam/sync 80 --shards=2 --shard=0
  0            */4 * * *   php yii steam/discover 500
  30           4   * * *   php yii steam/get-coming-soon
  0            6,18 * * *  php yii sale/synchronize
  0            6   * * *   php yii sitemap/generate
  0            8   * * *   php yii cache/flush-all
  */5          *   * * *   php yii import/all
  0            4   * * 7   php yii geo-ip/update
  0,15,30,45   *   * * *   php yii instant-gaming/match
  7,22,37,52   *   * * *   php yii instant-gaming/refresh-prices
